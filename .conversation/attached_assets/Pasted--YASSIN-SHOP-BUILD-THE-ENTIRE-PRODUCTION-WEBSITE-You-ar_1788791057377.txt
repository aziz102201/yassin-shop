# YASSIN SHOP — BUILD THE ENTIRE PRODUCTION WEBSITE

You are the lead software engineer, senior frontend engineer, senior backend engineer, security engineer, UI/UX engineer, QA engineer, and release engineer for this project.

Your job is not to explain how to build the website.

Your job is to **build it**.

Do not behave like a tutorial assistant.
Do not give me a list of implementation steps and wait for approval.
Do not repeatedly ask me questions that can be answered by inspecting the repository, assets, existing configuration, or by making a reasonable professional engineering decision.

Take ownership of the implementation from start to finish.

The final result must feel like it was produced by a very strong professional software engineer for a real business—not generated filler, not a template with arbitrary components, not an oversized demo, and not "AI slop."

---

# 1. THE PRODUCT

Build the production website for **Yassin Shop**, a real retail shop.

The website is a customer-facing online storefront whose primary purpose is to:

* present the shop professionally
* showcase its real products
* let customers browse products easily
* inspect product details
* select relevant variants such as size/color when applicable
* understand pricing and availability
* place an order/contact the shop through the intended ordering mechanism
* work exceptionally well on mobile
* look trustworthy enough that a real customer would comfortably buy from it

The website must be designed around the actual business rather than around generic ecommerce boilerplate.

The business is in Tunisia, so the experience should feel appropriate for Tunisian customers:

* TND pricing
* Tunisian phone/contact conventions where applicable
* French and/or Arabic content when supported by the available business information
* excellent Arabic RTL support if Arabic is included
* mobile-first behavior
* practical ordering flow appropriate for how the shop actually sells

Do not invent business facts.

Do not invent products.
Do not invent prices.
Do not invent sizes.
Do not invent colors.
Do not invent stock.
Do not invent delivery promises.
Do not invent payment methods.
Do not invent addresses, phone numbers, social accounts, policies, or legal claims.

Use the real information and assets available in the repository/project.

Where real business information is genuinely missing, build the system so the information can be supplied cleanly through the intended content/data layer rather than hardcoding fake facts into the customer experience.

# 14. SECURITY

Assume the website will eventually be exposed to hostile internet traffic.

Apply production security practices throughout the application.

At minimum:

* validate all untrusted input server-side
* never trust client-side validation
* never trust client-provided prices
* never trust client-provided stock state
* prevent unauthorized data access
* prevent IDOR-style access to protected resources
* protect server-only secrets
* never expose environment secrets to the client
* use safe authentication/authorization patterns where authentication exists
* protect state-changing operations
* sanitize/escape user-generated content where relevant
* avoid SQL injection
* avoid XSS
* avoid open redirects
* avoid unsafe URL handling
* avoid insecure file handling
* avoid dangerous dynamic evaluation
* use secure cookies/session configuration where applicable
* apply appropriate security headers
* prevent sensitive data from appearing in client bundles
* avoid leaking stack traces or internal errors in production
* handle errors without exposing implementation details

Do not add security theater.

Implement actual security controls appropriate to the architecture.

# 15. DATA INTEGRITY

* do not calculate an important business value differently in multiple places
* do not let the client become authoritative for price
* do not allow stale client state to overwrite authoritative server data
* do not duplicate database truth into arbitrary local constants
* do not create inconsistent parallel representations of products

When there is a conflict, the authoritative server/data layer wins.
